# v0.2 plan — from harness to product

Status: implemented · 2026-09-24 (see "Outcome" at the end)

## Who it is for

| Persona | Needs |
|---|---|
| **Operator** (Instinct user) | a phone the agent can use without their laptop; a number for 2FA; control of risky actions from their real phone; a way to step in (Google sign-in, CAPTCHA); a record of what happened |
| **Agent** (Instinct, Claude Code, any MCP/HTTP client) | a URL and a token; instructions it can read itself; tools that return compact screens |
| **Contributor** | CI, a contributing guide, a security policy, an honest compatibility story |

v0.1 served local agents well. It did not serve a cloud agent that cannot install software.

## Journeys (acceptance tests for "working product")

1. **Try it** — `npx github:niravjaiswal/agent-phone-harness demo` works on a clean machine. (Package is not on npm; README currently tells people to run a command that 404s.)
2. **Mac → Instinct** — `agent-phone up && agent-phone serve --public` prints a connection block Instinct can use, and an operator panel link.
3. **Always-on** — on a Linux VM, one script brings up phone + harness + tunnel and prints the same block.
4. **2FA** — operator connects a number (Telnyx/Twilio webhook, relay phone, or IMAP); `phone_wait_for_otp` finds codes from it.
5. **Approval** — gated action pings the operator's phone; they approve in the panel; agent proceeds.
6. **Handoff** — agent hits a CAPTCHA/sign-in wall, asks for a human; operator takes control in the panel, hands back.
7. **Oversight** — operator sees live screen, sessions, traces; can end a session.

## Found during the survey (bugs, fix first)

- `serve()` builds **two Harness instances** — MCP sessions invisible to REST/operator.
- One `StreamableHTTPServerTransport` for the whole server — only **one MCP client ever**; a reconnect fails.
- **Agent can approve its own action**: `/approvals/:id/approve` uses the agent token.
- **Agent can opt out of gating**: `mode: "autonomous"`, `allowShell`, `allowInstall` accepted from the agent.
- `~/.agent-phone/policy.json` is declared in `paths` and **never loaded**.
- `phone_clipboard` bypasses policy and audit.
- Loopback server with no token accepts `text/plain` POSTs → CSRF from any web page the operator visits.
- Implicit session resolution (`sessionId` omitted) is global — agent A could drive agent B's session.
- README and `avd.ts` link docs that do not exist (`docs/compatibility.md`, `docs/setup/telephony.md`).

## Decisions

**Two credentials.** Agent token: `/mcp`, `/sessions/*`, `/devices`. Operator token: panel, approvals, secrets,
takeover, config. Server refuses to start if they are equal. Panel exchanges the operator token for an
HttpOnly SameSite=Strict cookie; cookie-authenticated writes also require a custom header (CSRF). Cross-origin
requests are refused outright.

**Operator ceiling.** `policy.json` (or `PHONE_POLICY_FILE`) is the ceiling. Agent-supplied policy can only
narrow: mode = min, capability flags = AND, blocked lists = union, allowlists = intersection, budgets = min.
Default ceiling is `guarded`. Local shell users are operators by definition (they can edit the file).

**Leases.** One session per device. Busy devices are skipped by auto-pick. Idle sessions reaped over HTTP.
Sessions are owned by the MCP connection that opened them; implicit resolution is per-owner.

**Operator control pauses the agent.** Taking control in the panel makes agent mutations fail with
`device_busy` until released. Enforced at the device wrapper, so no mutation path can skip it.

**Messages are a hub, not a device feature.** `MessageSource`s: device SMS, device notifications, webhook
inbox (Telnyx Ed25519, Twilio HMAC-SHA1, relay bearer token), IMAP (no dependency; minimal client).
OTP extraction ranks keyword proximity, never returns a code twice in a session, and can type the code
without returning it.

**Identity.** Operator sets the phone number and email; the agent sees them at session start (it needs to
know what number to type into a signup form).

**Handoff is an approval with a different type.** `phone_request_human` → push → panel "take control" →
"hand back" decides it. Reuses the store, the notification path and the panel.

**Notifications.** ntfy, Telegram, Slack, generic webhook. Links to the panel; never carries the evidence
screenshot or a token.

**Per-client MCP transports sharing one Harness.** Unknown session id → 404 so clients re-initialize.

**Tunnel.** cloudflared quick tunnel by default (no account), named tunnel via `CLOUDFLARE_TUNNEL_TOKEN`.
Public URL from `PHONE_PUBLIC_URL`, else discovered from cloudflared's `/quicktunnel` metrics endpoint
(compose) or its stderr (local `--public`).

**Container.** Harness image = node:22-slim + Debian `adb` (Google ships Linux platform-tools for x86_64 only).
Harness keeps `adb connect` alive to `PHONE_ADB_CONNECT` targets so a restarted redroid comes back.
Port 5555 is never published.

**Agent onboarding.** Public `/agent.md` with instructions and the server's own URL; REST `?format=text`
returns the same compact rendering MCP does.

**No new runtime dependencies.** Ed25519/HMAC from `node:crypto`, IMAP over `node:tls`, panel is one
vanilla HTML page.

## Build order

1. Foundation — config + tokens, ceiling, leases/ownership/idle reaper, operator control, clipboard fix
2. Messages — hub, inbox, webhooks + signatures, IMAP, OTP ranking/dedupe/type, identity
3. Notify + handoff
4. HTTP server — route split, auth, per-client MCP, operator API, agent.md, text format
5. Operator panel
6. Tunnel + `serve --public` + CLI (`token`, `inbox`, `number`, `notify test`)
7. Container — Dockerfile, deploy/compose.yml, install.sh
8. Docs + OSS scaffolding (CI, release, SECURITY, CONTRIBUTING, templates) + README; `prepare` script so
   `npx github:` works
9. Real-device validation on redroid if the local VM kernel has binder

## Out of scope

Hosted multi-tenant service (billing, abuse, per-tenant isolation) — a business decision, not a harness
feature. iOS parity for the hosted path. Publishing to npm (needs the owner's credentials).

## Outcome

All eight build steps shipped; step 9 moved to CI (see below). 265 tests.

Verified by hand, beyond the test suite:
- The panel on a phone-sized viewport: live screen, take control → agent gets `device_busy` →
  hand back → the agent's waiting `request_human` returns `done`; approvals; setup forms; activity.
- The cloud-agent path over the real internet: `serve --public` through a Cloudflare quick tunnel,
  then REST (`?format=text`) and an MCP client over the public HTTPS URL — session, batch login,
  OTP entered for the agent, verify.

Found and fixed during verification:
- Tunnel URL parser accepted `https://api.trycloudflare.com` out of a cloudflared error line.
- Setup page overflowed a phone screen (grid tracks growing to fit long webhook URLs).
- Every visitor behind the tunnel shared one login rate-limit bucket (operator lockout).
- `Secure` cookie decided from the public URL rather than the request.
- Stale approvals from ended sessions lingered; approval history grew without bound.
- Panel re-rendered every 5 s, wiping text the operator was typing.
- Offline Apple Watch simulators were offered as "phones".

Not done here, and why:
- **Real-Android validation.** This machine had ~200 MB of free disk (swap pressure), so no emulator
  image or redroid container could run. Moved to CI: `.github/workflows/android.yml` runs
  `scripts/e2e-android.mjs` against Android 11 and 14 emulators, and exercises `agent-phone up` itself.
- **Container image build.** Same reason. CI builds and smoke-tests it (`ci.yml` → `container`).
- **npm publish.** Needs the owner's credentials; `release.yml` publishes on a tag when `NPM_TOKEN` is set.
  Until then the README installs from GitHub.
